漏洞类别：破坏防自动化 / 业务逻辑缺陷

挑战目标：以同一个用户的身份，给任何一个商品评论（Review）至少点赞三次。

2. 漏洞发现线索与复现过程

在正常的业务逻辑中，点击“点赞”按钮时，前端会立刻禁用该按钮。即使你拦截请求重发，后端通常也会有类似这样的防刷逻辑：
这就是典型的“检查时间与使用时间”。如果我们能在极短的时间内向服务器同时发送几十个相同的点赞请求，后端的多个线程会“同时”去查询数据库。此时数据库还没有来得及写入第一条点赞记录，所有线程查询到的结果都是“该用户没点过赞”，于是它们全部放行，集体执行了 `+1` 操作！

3. 实战危害与加固建议
实战危害展示：
条件竞争是电商、金融系统中最致命的逻辑漏洞之一。点赞功能的竞争最多导致数据注水，但在实战中，这种手法常被红队用于“双花攻击（Double Spending）”。例如：在账户余额只有 100 元时，并发发起 20 笔“提现 100 元”的请求。如果后端的扣款逻辑存在条件竞争，这 20 个线程都会认为余额充足并放行，最终黑客可以利用 100 元的本金直接提现 2000 元，对企业造成灾难性的直接经济损失。

修复方案：
1. 数据库级的唯一性约束：最底层的防线是在数据库表结构上建立联合唯一索引。比如在 `likes` 表中对 `(user_id, review_id)` 建立 UNIQUE 约束。即使多线程并发尝试写入，数据库引擎也会在底层抛出违反唯一约束的异常，从而阻断事务。
2. 悲观锁：在处理敏感的“查后写”逻辑时，使用数据库锁，强制让并发读取该条记录的线程排队串行执行。
3. 乐观锁：在表中加入 `version` 字段。每次更新时验证版本号 `UPDATE ... SET likes = likes + 1, version = version + 1 WHERE id = ? AND version = 旧版本号`。只有第一个到达的线程能更新成功，后续并发请求会因版本号不匹配而失效。
