漏洞名称：历史依赖拼写劫持 / 软件供应链投毒

1. 挑战概述
漏洞类别：软件供应链安全 / 恶意组件引入

挑战目标：通过审查企业历史遗留的软件物料清单，找出一个曾经被开发团队误引用的“拼写劫持”恶意依赖包，并将其报告给官方。

2. 漏洞发现线索与复现过程

在安全审计中，我们不仅要检查已知漏洞，还要用极高的敏锐度去审查 `package.json` 中的每一个包名，寻找开发人员因“手误”而引入的供应链毒药。

1. 打开package.json.bak，里面记录了系统早期版本使用的依赖库清单。
2. 发现，列表中存在一个名为 `epilgoue-js` 的依赖库。正版的名字应该是 `epilogue-js`。这里 `logue` 被拼写成了 `lgoue`。这是一个极其典型的 Typosquatting 供应链投毒包。

3. 实战危害与加固建议
实战危害展示：供应链投毒是目前企业防不胜防的降维打击。黑客在伪造的包中通常会写入 `preinstall` 脚本，一旦开发人员手滑执行了 `npm install epilgoue-js`，恶意脚本就会在服务器或开发机上静默执行，直接反弹 Shell、窃取环境变量中的 AWS 秘钥，甚至在编译期间将后门植入到企业最终发布的产品中。

修复方案：
1. 建立私有依赖镜像与包名白名单：企业绝不能让生产环境的 CI/CD 直接从公共 npm/PyPI 源拉取包。必须搭建私有源，并开启严格的依赖审查。所有新引入的第三方包必须经过安全团队的自动扫描与审批后，才能加入企业白名单。
2. 强制使用锁文件：在项目代码库中必须提交并锁定 `package-lock.json` 或 `yarn.lock`。这些文件锁定了依赖的精确版本和完整性哈希值。即使公共源上的包被篡改，哈希校验失败也会立即阻断构建。
3. 引入供应链安全防护工具：使用 Socket.dev、Snyk 等专注于检测供应链投毒的工具，自动拦截包含异常网络请求、高危安装脚本以及包名与流行库极度相似的恶意组件。
