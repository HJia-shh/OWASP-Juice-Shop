漏洞名称：GDPR 数据窃取 / 注册校验与数据导出逻辑不一致

1. 挑战概述
漏洞类别：业务逻辑缺陷 / 身份验证破坏

挑战目标：在不使用 SQL 注入的情况下，利用系统注册模块与 GDPR 数据导出模块之间的校验差异，窃取其他用户的个人敏感数据。

2. 漏洞发现线索与复现过程

在 Web 安全中，“创建相似账户”是一种高级的业务逻辑绕过手法。如果在用户注册时，后端没有对邮箱字段执行严格的 `trim()`清洗，而在执行数据导出或查询时，数据库又默认忽略了尾部空格，攻击者就可以伪造一个“看似不同，实则指向同一人”的幽灵账户。

3. 实战危害与加固建议
实战危害展示：这种被称为“账户同名欺骗”的漏洞，在真实的互联网大厂中也屡见不鲜。由于现代企业往往采用微服务架构，“账号注册”和“合规导出/密码找回”通常是不同的团队开发的两个独立服务。如果两边对字符串清洗的标准不一致，黑客就能通过“加空格”、“加不可见 Unicode 字符”或“大小写混用”创建出高仿账户，进而接管受害者资产或窃取机密 PII。

修复方案：
1. 全局一致的数据清洗中间件：在网关层或后端框架的最前端，部署全局的输入清洗逻辑。强制对所有请求中的 `email`、`username` 等关键字段执行严格的 `trim()` 和统一的小写化处理，确保数据流转到任何微服务时都是标准化的干净格式。
2. 数据库约束：在底层数据库层面，将 `email` 字段设置为 `UNIQUE`，并在插入前由数据库触发器或 ORM 框架进行强制规范化校验，确保底层数据绝对不可能出现同名异变数据。
