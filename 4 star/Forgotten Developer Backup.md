漏洞名称：开发者备份文件泄露 / 空字节截断与白名单绕过

1. 挑战概述
漏洞类别：安全配置错误 / 不当的输入验证

挑战目标：访问开发者遗忘的备份文件。

2. 漏洞原理与机制分析

在 Web 服务端处理文件下载请求时，若采用简单的字符串后缀匹配来实施访问控制，而未对 URL 编码的控制字符进行严格清洗，往往会引发应用层与底层操作系统之间的解析不一致。

1. 在/ftp目录下下载package.json.bak` 即可
2. 由于仅允许访问 `.md` 和 `.pdf` 格式的文件。后端路由层部署了基于文件扩展名的白名单过滤逻辑。
3. 空字节双重编码为 %2500被视为字符串的终止符。当底层读取文件流遇到空字节时，会自动忽略其后的所有字符，直接打开空字节之前的真实文件名。
4. 和前面挑战一样，直接在后面加上%2500.md即可

3. 实战危害与加固建议
实战危害展示：开发者备份文件是高价值目标。一旦此类文件泄露，外部人员不仅能直接摸清系统的完整技术栈、第三方依赖库精确版本号，还可能从备份配置中直接提取到硬编码的数据库连接串、API 密钥或内部开发注释。

修复方案：
1. 规范化构建与发布流水线：在代码打包与容器镜像构建阶段，必须配置严格的 .dockerignore 或构建清理脚本，严禁将任何带有 `.bak`、`.old`、`.swp`、`.git` 等后缀的开发备份及版本控制文件发布到生产环境的 Web 可达目录中。
2. 严格的路径净化与空字节拦截：在接收任何涉及文件路径的用户输入时，后端应在进入业务逻辑前强制执行字符白名单过滤，直接拦截并拒绝任何包含空字节`\0`、`%00`或路径遍历符`..`的非法请求。
3. 采用静态资源映射机制：避免直接将用户的输入参数拼接到底层文件系统调用中。应通过数据库或内存字典维护一份“公开文件 ID 与实际存储路径”的映射表，用户仅能通过文件 ID 请求授权范围内的资源，从架构层面彻底消除文件名解析截断的风险。
